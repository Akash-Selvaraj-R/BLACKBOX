Section 07.1

FRONTEND ARCHITECTURE

The application is a single-page Next.js App Router build: one root layout, one route, and one client component that owns every operating surface.

Build stack (as implemented)

React 19 with TypeScript 5.7 under strict: true. Tailwind CSS 4 is loaded through @tailwindcss/postcss, and the product's visual identity lives in a hand-written Neo-Brutalist stylesheet (app/globals.css, ~13.8 KB) rather than in generated component classes. Vite is not used — bundling and dev server come from Next.js 16 (Turbopack), as shown by the build output.

Route handling is deliberately minimal: app/page.tsx returns <BlackboxCommandCenter /> and nothing else. Navigation between screens is client-side state, not routing.

Scope discipline

There is no FILES screen, no PERFORMANCE screen and no SETTINGS screen in the code. The settings-like surface is named SYSTEM, and file browsing is represented by the folder grid inside WORKSPACE. This report documents the surfaces that exist, not the ones the concept implies.

No global store, no context provider, no router state, no side-effect hooks. Everything re-renders from six pieces of local state in the shell component.

Transitions (verbatim logic) 
startTask()  : if command empty -> no-op
               else taskState = 'approval'
approveTask(): taskState = 'running'
               setTimeout(+900ms) -> 'complete'
cancel       : taskState = 'idle'
NEW TASK     : taskState = 'idle', command = ''
GENERATE PLAN: disabled while taskState = 'running'
Pipeline progress mapping 
steps = OBSERVE, UNDERSTAND, PLAN, APPROVE,
        EXECUTE, VERIFY, REPORT

activeUntil = approval -> 3   (APPROVE waiting)
              running  -> 5   (through VERIFY)
              complete -> 6   (all seven DONE)
              idle     -> -1  (all IDLE)

Interaction and accessibility
  • aria-label on the menu toggle and the main navigation landmark.
  • htmlFor / id pairing on the COMMAND textarea.
  • :focus-visible outline: 3 px cobalt with 3 px offset on buttons and textareas.
  • prefers-reduced-motion disables all transitions.
  • Disabled state on GENERATE PLAN while running or when the command is empty.
  • Two breakpoints: 900 px (grid collapse) and 700 px (off-canvas nav).
Typography

Display: Arial/Helvetica at weight 900–950, tight negative tracking, headlines up to ~94 px. Technical labels: ui-monospace at 8–11 px, 800–900 weight, 0.1–0.18 em letter-spacing. Every panel heading, stamp and status chip uses the mono voice; every headline uses the display voice.

Section 08

BACKEND ARCHITECTURE

Status: target architecture — no backend exists in this repository

There is no FastAPI (or any other) service, no API route, no request/response model, no orchestration process, no executor, no verifier and no task persistence layer in this repository. A repository-wide search returns zero occurrences of fetch(, database clients and streaming primitives. The page is statically prerendered. This section therefore documents the intended backend contract that the implemented interface already assumes — and it is labelled as target throughout.

What the backend would own
ConcernPlanned responsibility
RoutesPOST /tasks · GET /tasks/{id}
POST /tasks/{id}/approve
POST /tasks/{id}/cancel
GET /tasks/{id}/events (SSE)
GET /workspaces
ModelsPydantic-style request/response schemas: TaskCreate, Plan, Operation, Approval, TaskResult, Event.
OrchestrationDrive the seven stages, hold cancellation, emit stage transitions.
ExecutionApply approved operations only, inside the authorized workspace scope.
VerificationRe-read the workspace and compare against the planned operations.
PersistenceStore run, plan, approval decision, operations and verification outcome.
StreamingPush stage/operation events to the UI while a task runs.
What actually serves the app today
  • Next.js server prerenders a single static route at build time.
  • Metadata API in app/layout.tsx sets title, description, favicon set and theme colours for light/dark.
  • Vercel Analytics mounts only when NODE_ENV === 'production' — the sole network integration in the codebase.
  • All task logic runs in the browser as React state; there is no server round trip in the task flow.
Interface the UI already implies 
Task   { id, title, state, steps[7], queue }
Plan   { folders, moves, renames, index }
Event  { time, stage, message }
Report { files, operations, errors, verification }

state  : idle | approval | running | complete
gate   : no execution before approval

These four shapes are all the front end needs; a future service can implement them without any change to the interface.

Why the gap is acceptable at this stage

The submission is an interface-first build: the control contract (plan → approve → execute → verify → report) is defined and demonstrable before the runtime exists, so safety semantics are fixed early rather than retro-fitted. Section 21 lists the service layer as the first future work item.
