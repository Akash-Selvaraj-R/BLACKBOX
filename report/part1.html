Section 01

ABSTRACT

BLACKBOX is a privacy-first local AI operating layer for AI PCs: it turns a plain-language command into an observable, approvable, verifiable sequence of workspace operations instead of an instant, unauditable answer.

The problem it addresses is simple. Cloud assistants move private workspace context off the machine, and when an agent does act on files, the user rarely sees what was planned, what was approved, or whether the result matched the plan. BLACKBOX restructures that interaction into an explicit pipeline — OBSERVE → UNDERSTAND → PLAN → APPROVE → EXECUTE → VERIFY → REPORT — where nothing executes until a human approves a concrete list of proposed operations, and the run ends with a verification and a report rather than a chat message.

The repository delivers this contract as a working interface layer: a Next.js 16 + React 19 + TypeScript application with eight operating surfaces (COMMAND, WORKSPACE, TASKS, ACTIVITY, AGENTS, MODELS, REPORTS, SYSTEM), a four-state task lifecycle with a hard approval gate, and a Neo-Brutalist design system that makes system state legible at a glance. All task state is held in the browser; the app issues no model or file system requests of its own.

The inference runtime, file-system executor, and persistence layers are specified in this report as clearly-labelled targets so that local models (ONNX / AI-Hub-style runtimes on CPU, GPU or NPU) can be added behind a provider abstraction without changing the interaction contract. The result is a system designed so that intelligence stays on the machine, actions stay controlled, and every action stays reviewable.

Section 02

PROBLEM STATEMENT

Assistants are optimised for response speed, not for controlled action inside a private workspace. Six gaps make them hard to trust with real files.

01 — Cloud dependency

Most assistant workflows assume a hosted model. Workspace context — file names, project structure, document content — has to leave the device before anything useful happens. For internship reports, client material or internal code, that transfer is the objection, not the latency.

02 — Private workspace exposure

A personal or work workspace is not a prompt. It is a live tree of folders with permissions, drafts and half-finished material. Treating it as model input blurs the boundary between "readable by me" and "readable by a remote service".

03 — Opaque local file interaction

When a tool does touch local files, the user typically sees the result after the fact: folders renamed, documents moved. What was scanned, what was inferred and which operations were considered is rarely visible.

04 — No transparent execution

There is usually no durable record connecting the original request to the individual operations performed, so "it sorted my projects" cannot be decomposed into checkable steps.

05 — Missing human control point

Automation either happens immediately or requires the user to pre-configure rules. There is no middle state where the system proposes exact operations and waits for a person to accept or cancel them.

06 — No auditable outcome

Without verification against the plan and a final report, a user cannot answer the questions that matter: what changed, what failed, and whether the result is what was asked for.

What BLACKBOX does not claim

This repository does not claim to have defeated these problems end-to-end. It implements the control surface for them — the approval gate, the pipeline state machine, the plan and report views, and the local-only data-route declarations — and it specifies the runtime layers that complete the loop. Sections 08, 16 and 20 state precisely where the boundary sits.

Design requirement derived

Any future BLACKBOX runtime must satisfy five conditions:

1. context stays on device
2. every operation is listed before it runs
3. a human approves the list
4. results are verified against the plan
5. the run ends in a readable report

PROPOSED SOLUTION

BLACKBOX is a local-first operating layer: a control plane between a person and their machine that converts intent into approved, executed and verified work.

USER issues a plain-language command
↓
COMMAND intent captured in the COMMAND surface
↓
OBSERVE scope the authorized workspace
↓
UNDERSTAND classify structure and intent
↓
PLAN produce an exact operation list
↓
APPROVE human gate: approve or cancel
↓
EXECUTE apply approved operations only
↓
VERIFY check results against the plan
↓
REPORT evidence: counts, status, route
Why each stage exists
StageReason it is a separate step
COMMANDSeparates intent capture from execution, so a typed request is a draft, not a trigger.
OBSERVEEstablishes what is in scope before any interpretation, and defines the authorization boundary.
UNDERSTANDTurns raw structure into meaning, so later steps reason about projects, not just paths.
PLANConverts meaning into discrete, countable operations that a human can actually read.
APPROVEThe single point where authority passes from system to person and back; nothing runs before it.
EXECUTEApplies exactly the approved list, keeping the blast radius bounded and predictable.
VERIFYDetects drift between plan and outcome; without it, "done" is an assumption.
REPORTCompresses the run into auditable evidence the user can keep or re-check.
Implementation status

IMPLEMENTED The seven stages are rendered as a live pipeline in the COMMAND surface, and stage progress is driven by the real task state machine (components/blackbox-command-center.tsx:80).

TARGET Stage internals (scanning, model reasoning, file writes, verification checks) are the runtime described in Sections 08 and 09; they are not present in this repository.
